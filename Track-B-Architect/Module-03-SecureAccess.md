# Module 03 — Secure Access | Track B

**Core content (points the facilitator must cover):**

1. **The `grantControls: mfa` trap for agents:** A CA policy using `mfa` as a grant control on agent identities is **silently invalid** — it neither blocks nor authenticates. The agent cannot complete interactive MFA, and the policy generates no enforcement event in the logs. The only valid option to block an agent with CA is `"builtInControls": ["block"]`. This is not a bug — it is documented in the CA for workload identities reference.

2. **Blueprint-level CA as a scaling pattern:** Creating a CA policy per agent instance fails at scale. The correct architecture is a Blueprint-level CA policy using `clientApplications.includeAgentIdServicePrincipals` to cover all current and future agent identities derived from the same blueprint — without per-instance configuration.

3. **Applicable Microsoft controls:** Entra CA for Agents with `clientApplications.includeAgentIdServicePrincipals` enables agent-specific policies. Entra ID Protection evaluates service principal risk and can feed CA conditions. PIM just-in-time limits the elevated permission exposure window. Defender for Cloud Apps audits OAuth consent and surfaces application anomalies.

4. **OAuth consent as a silent accumulation vector:** An agent can accumulate additional permissions without any administrator explicitly approving them if the consent flow is unrestricted. The signal is in `AuditLogs` under `Add delegated permission grant` — without correlation to an approval event, it is a drift indicator.

5. **Credential isolation for non-managed-identity agents:** Managed identity (Azure-native, no credential on disk) is the correct architecture for agents running on Azure infrastructure. For agents running outside Azure — open source agents, local agents, third-party platforms — the token management problem is structurally different and typically solved insecurely: the real token lands inside the agent environment where it can be exfiltrated, committed to a git repo, or abused if the agent is compromised. The recommended pattern for these scenarios is a **placeholder token / proxy architecture**: a broker service issues the agent a placeholder JWT (signed by the broker, useless to any third party), and all API calls route through a proxy that intercepts the placeholder, verifies the broker signature, and swaps in the real token before forwarding. The agent never holds a real credential. For environments with SPIFFE/SVID support, the placeholder JWT can embed a representation of the agent's client certificate, enabling mTLS binding at the proxy — the token can only be used from the instance it was issued to. Reference: RFC 8705 (OAuth 2.0 mTLS), fly.io token proxy pattern (2023), Matthew Garrett (2026). Microsoft equivalent: managed identity + Key Vault references eliminates the problem entirely for Azure-hosted agents.

   > **Enterprise-scale validation — credential brokering vs. credential injection:** Roblox's account of securing internal coding agents (Harshit Kumar, Jaskaran Singh, Ahmad Alomari, "Caging the Agent", BlackHat USA 2026) confirms this pattern and adds a distinction worth adopting. **Credential brokering** — the pattern described above — still exposes the short-lived token in the agent's memory, which remains vulnerable to prompt injection if the agent can be induced to leak its own context. **Credential injection** goes one step further: a mediating gateway intercepts the outbound call and injects the provider credential at request time, so the agent never sees the real token at all, not even briefly in memory. The difference is between "the token is short-lived" and "the token never exists inside the agent process." For third-party MCP servers (Module 07, Domain D) this is the target architecture, not the simple broker. A second finding from that deployment, after four weeks of real operation: trusted domains such as GitHub can be used to exfiltrate data under standard endpoint permissions — the "allowlist paradox." Allowing a trusted domain is not the same as allowing any traffic to that domain; egress filtering must validate usage pattern, not destination alone.

6. **CNAPP for Azure-hosted agent workloads:** If agents run as containerized workloads on Azure (AKS, Container Apps, Azure Functions), Defender for Cloud (CNAPP capability) extends security posture management to the infrastructure layer: container vulnerability assessment, runtime threat detection, and misconfiguration alerts for the environment hosting the agent. This is complementary to the identity and access controls covered in this module — Entra Agent ID secures the agent identity, CNAPP secures the compute it runs on. Enable the Defender for Containers plan in Defender for Cloud for any Azure subscription hosting agent workloads.

   > **Licensing change, effective 1 July 2026:** AI agent discovery and security posture for Microsoft Foundry agents and third-party cloud agents now require a **Microsoft Agent 365 license**. This capability was previously included in the Defender CSPM plan. Defender CSPM still discovers Foundry accounts and projects, but agent-level inventory and posture now live in the AI agent inventory in the Microsoft Defender portal, gated behind Agent 365. Verify Agent 365 licensing is active in the demo tenant before running this module's lab — the same license already required for `AgentsInfo` in Module 01. Reference: [Transition AI agent security capabilities to Microsoft Agent 365](https://learn.microsoft.com/defender-xdr/security-for-ai/transition-agent-security-to-agent-365).

7. **Interactive (OBO) vs. Autonomous (client credentials) — two identity patterns with different attack surfaces:** Microsoft Entra Agent ID distinguishes two fundamental agent identity patterns with distinct security profiles. *Interactive agents* act on behalf of a signed-in user using the **on-behalf-of (OBO) flow** with delegated permissions — the risk is an agent misusing inherited user permissions or the user being unaware of what the agent executes in their name. *Autonomous agents* authenticate with their **own agent identity via client credentials flow** — no user in the loop; the risk is an agent operating without constraint if the identity has excessive permissions and no CA policy enforces a limit. A third pattern, the **agent's user account**, pairs 1:1 with an agent identity to give the agent a mailbox, Teams membership, and calendar — use only when the agent must access systems requiring a user object; risk: compromised agent joins meetings under false pretenses, sends communications as a trusted team member, or reads documents through collaborative access. Each pattern requires a distinct CA targeting strategy: OBO → target user + agent combination; autonomous → target agent identity blueprint (all instances inherit); agent user account → separate CA policy scoped to agent user object type.

   > **Named CA templates now available (updated June 2026):** Microsoft ships purpose-built Conditional Access templates that map directly to these two patterns, replacing hand-built policies: **On behalf of agent access policy** for the OBO pattern, and **Autonomous agent access policy** for client-credentials and agent-user-account patterns — the latter includes an **Agent execution environments (Preview)** condition to scope device-compliance requirements specifically to agents running on managed endpoints like Windows 365 Cloud PCs for Agents, without over-scoping the policy to interactive users. At scale, **Custom Security Attributes** let a single policy target every agent carrying a matching business-defined label (e.g., `dataClassification: confidential`), including agents created after the policy is written — the attribute-driven equivalent of blueprint-level targeting for cases that cut across multiple blueprints. **Licensing:** Conditional Access for agents requires Microsoft Entra ID P1 or P2 **plus a Microsoft Agent 365 license per user** — plan this into the demo tenant checklist alongside the Agent 365 requirement already noted in Module 01. **Hard boundary to communicate in the lab:** Conditional Access only protects resources secured by Microsoft Entra ID — an agent authenticating with a raw API key bypasses the Entra token pipeline entirely, and no CA policy applies. This is the exact justification for the placeholder-token/proxy pattern in point 5 above: without it, non-managed-identity agents sit outside CA's reach by design, not by misconfiguration. Reference: [Conditional Access for agents](https://learn.microsoft.com/entra/identity/conditional-access/agent-id), Microsoft Learn.

8. **Identity Protection for agents — risk signals for non-human identities, and the exact policy to wire them to CA:** Microsoft Entra ID Protection detects anomalous activity for agent identities and generates risk scores from: (a) the agent's own actions (unusual authentication, out-of-scope resource access, high-velocity operations, reconnaissance-like Graph calls); (b) risk inherited from the sponsor (sponsor account compromise propagates to their agent identities). Risk signals feed directly into CA through the **Agent risk (Preview)** condition — a policy scoped to **All agent identities**, target **All resources**, condition Agent risk = High, grant = Block, blocks every instance flagged High in a single evaluation. Microsoft ships this exact policy as a template at `aka.ms/CreateAgentRiskPolicy` rather than requiring it be hand-built. The same condition applies to **agent user accounts** (agents with mailboxes/Teams membership) by targeting **All agent users** instead — configure Medium and High there, since agent users interacting like humans warrant a lower bar than autonomous back-end agents. Always deploy in **Report-only** mode first and review policy impact before enforcing.

    This creates a detection-to-containment chain for non-human identities: Identity Protection flags risk → CA blocks new token issuance → sponsor notified → human reviews and remediates. **The chain has a real gap worth stating in the lab:** the CA block only stops future authentication attempts; it does not revoke sessions already granted before the risk was flagged. Session revocation (Module 02, point 10, L1) closes that gap and is not optional if you're relying on this chain for actual containment, not just future prevention. Reference: [Identity Protection for agents](https://learn.microsoft.com/en-us/entra/id-protection/concept-risky-agents); [Recommended policies for autonomous agents](https://learn.microsoft.com/entra/identity/conditional-access/policy-autonomous-agents), Microsoft Learn.

9. **Global Secure Access for agents — network-level control plane:** Microsoft Entra Global Secure Access (GSA) adds a network enforcement layer independent of agent identity: (a) log all agent network activity (API calls, MCP server connections, web requests) to remote tools for audit and threat detection; (b) **web categorization** controls which APIs and MCP servers agents can reach — an agent cannot connect to an uncategorized or blocked MCP server even if its identity is authorized; (c) file upload/download restrictions by file type; (d) threat intelligence-based filtering blocks known malicious destinations automatically. Most architecturally significant for agentic security: GSA includes **prompt injection detection at the network level** — detecting and blocking attempts to inject malicious instructions through data the agent processes, before those instructions reach the model. This is a control plane layer independent of the agent's reasoning context (same principle as CAGE in Module 02 point 5), implemented at the network rather than the application layer. Reference: [Secure Web and AI Gateway for agents](https://learn.microsoft.com/en-us/entra/global-secure-access/concept-secure-web-ai-gateway-agents).

10. **Microsoft Edge Controls for shadow AI prevention at the endpoint:** The repo's discovery approach detects shadow AI after it exists (`AgentsInfo`, `CloudAppEvents`). Edge adds a prevention layer: organizations can configure Microsoft Edge browser policies to **block work-account users from accessing consumer-grade AI applications** (ChatGPT, Gemini, Claude.ai, Copilot without enterprise license, etc.) from corporate devices. This is enforced via Microsoft Intune device compliance + Edge browser policies applied to the work identity — when a user signs into Edge with their corporate account, the policy restricts which AI destinations they can access. Combined with Defender for Endpoint local agent discovery (Module 01), this closes the shadow AI gap at both the browser layer (consumer AI SaaS) and the endpoint layer (locally running agents). Configuration path: Intune → Device Configuration → Edge browser policies → `AIGenAIDefaultSettings` or per-site content policies.

11. **Model extraction via API as IP theft and evasion vector:** An attacker with access to an Azure AI Foundry endpoint can reconstruct a proprietary model through systematic queries (input/output pairs), without needing direct model access. Signals: >500 inferences/hour from a single identity, high rate of distinct prompts, grid-pattern query sequences (decision space exploration). Correct access control: per-identity rate limiting in Foundry + monitoring with P03-Q6. This vector maps to OWASP LLM Top 10 2026, LLM06 — Unbounded Consumption (model extraction/theft was folded into this category in the 2026 edition, not a standalone item in the Agentic Applications Top 10), and is particularly relevant when the model was fine-tuned with proprietary data.

12. **The AI gateway is the crown jewel, and the wrong team usually deploys it:** This track recommends APIM as the enforcement point for MCP servers (Module 07, point 2) and cites rate limiting as an access control. The OffGuard research (Yaara Shriki, Wiz, DEF CON 34) into LiteLLM — the most widely deployed open source AI gateway, with 33,000+ GitHub stars and present in roughly a third of cloud environments according to Wiz telemetry — demonstrates why that enforcement point is itself the highest-value asset in the environment, and why the security team rarely deploys or audits it. A single proxy concentrates the API keys for every model provider, every prompt and response flowing through the organization, the connections to MCP servers, and the IAM role of the instance it runs on. Compromising the gateway does not mean compromising AI; it means compromising everything the gateway touches.

    **Three independent, responsibly disclosed paths from zero credentials to cloud compromise:**

    (a) **MCP authentication bypass through incorrect failure handling:** the MCP endpoint accepts two authentication methods — the gateway's own API key, or passthrough of an external OAuth2 token. When validation of the second method fails with a 401 or 403, the code catches the exception and returns an empty authentication object instead of rejecting the request. The result: an `Authorization: Bearer a` header carrying a single-character token produces a valid MCP session. No master key, no valid token, no prior knowledge of the target. The architectural lesson is not specific to LiteLLM: **an authentication failure that lands in a different code branch than the success path is a bypass surface**, and the correct pattern is to fail closed through a single rejection route, never to fabricate an empty identity as the result of an exception.

    (b) **Root RCE via custom guardrail, with the sandbox on the wrong endpoint:** the guardrails feature lets an administrator write Python that executes on every request. The test endpoint filters forbidden patterns and strips `builtins`; the production endpoint applies neither control and executes the code with `exec()` without a sandbox, in a container that runs as root by default. A single POST call authenticated with the credential from the documentation example (`sk-1234`, which a non-trivial share of deployments never rotate) yields a root shell with the database credentials, every provider API key, and mounted service account tokens, all in environment variables in plaintext. **The sandbox guarded the test door, not the production door.** That pattern is worth checking in any organizational control that exists in two separate code paths for the same function.

    (c) **SSRF that defeats IMDSv2 through application-layer header manipulation:** IMDSv2 requires a two-step handshake bound to specific headers, designed so a naive SSRF cannot complete it because it does not control the forwarded headers. The gateway strips a configured prefix before forwarding headers on its pass-through routes; an attacker prefixes the metadata header with that prefix, the gateway strips it, and the header arrives intact at the metadata endpoint. IMDSv2 is defeated not by a cryptographic failure but by an application-layer design decision that nobody evaluated against this use case.

    **The finding with the most operational impact: ghost guardrails.** Deleting a guardrail removes the record from the database and the UI confirms it no longer exists, but the code remains in the process's in-memory callback list and keeps executing on every request until the process restarts. An attacker with transient administrative access plants a malicious guardrail, deletes it to erase the evidence, and the code keeps running — undetectable to any control that trusts stored configuration as the source of truth. Detection requires inspecting live memory state, not declared config. This is the same class of gap MAESTRO Layer 5 describes for a compromised monitoring agent (Module 05, point 10).

    **Internet-scale validation:** a non-destructive scan of more than 3,000 internet-exposed instances found 6.2% with no authentication at all, 3.4% still using the unrotated credential from the documentation, and the MCP bypass confirmed on 330 instances. The researchers note this is the floor, not the ceiling: internal deployments, protected only by the assumption that they sit behind the VPN, are likely worse.

    **Direct consequence for this track's architecture:** the AI gateway — whether APIM, LiteLLM, or anything else — must be treated as critical identity infrastructure, with the same rigor as an IdP: default credential rotation verified at onboarding, separation between administrative UI credentials and API credentials, egress blocking from the gateway itself toward private IP ranges and the metadata endpoint (`169.254.169.254`), workload identity with minimal permissions instead of broad IAM roles inherited from the instance, and periodic audit that in-memory state matches declared configuration. No control in this point replaces the earlier ones in this module. They complement them exactly where those assume the gateway is already trustworthy.

    Reference: Yaara Shriki, "OffGuard: Breaking the Most Popular AI Gateway — from Authorization: Bearer a to Cloud Compromise", DEF CON 34, Wiz. Findings: GHSA-72m8-9m7m-h278 (MCP bypass), GHSA-7488-6r32-c95q (RCE, patched).

13. **`BehaviorInfo` — the audit trail for what real-time protection actually blocked:** Points 9 and 12 cover network- and gateway-level enforcement. Microsoft Defender's **real-time protection** for AI agents adds an enforcement layer at the point of tool invocation itself, and every decision it makes — audit or block — lands as a queryable record in the `BehaviorInfo` table (Advanced Hunting), not only as a UI notification. Coverage differs by platform: Agent 365 tool invocations routed through Work IQ MCP or onboarded customer MCP tools; Copilot Studio agents (Preview, requires the Copilot Studio connection); Foundry agents (Preview, the broadest coverage — user requests, agent responses, tool invocations, and tool responses); local agents, through Defender for Endpoint runtime protection (Module 01) rather than this path.

    **Two rule types, and the operational trap in how they interact:** the built-in **Default rule** audits every agent without stopping anything — this is how you validate what a rule would have blocked before enforcing it. **Custom rules** block matching high-confidence detection types, scoped to specific agents. The trap: **when a blocking rule covers an agent, near-real-time detection alerts stop generating for that agent** — audit mode keeps producing alerts, block mode does not. A SOC dashboard that goes quiet for an agent under a custom blocking rule is not evidence of no risk; it can mean the opposite, that risk is being silently blocked and the team stopped seeing it. Query `BehaviorInfo` directly rather than relying on the alert feed for agents under custom rules.

    **What lands in the table:** each behavior record includes the action type, the MITRE ATT&CK technique associated with it, the account and device involved, and a description of why the activity was flagged — enough to build a custom detection or feed a Logic App playbook (Module 05) without depending on the near-real-time alert stream. One coverage gap to flag explicitly: block events from Prompt Shields for Foundry and Copilot Agent Builder are recorded as behaviors today; the same is **not yet supported for agents built with Microsoft Copilot Studio** specifically. Reference: [Protect AI agents in real time using Microsoft Defender](https://learn.microsoft.com/defender-xdr/security-for-ai/ai-agent-real-time-protection); [`BehaviorInfo` (Preview) table reference](https://learn.microsoft.com/defender-xdr/advanced-hunting-behaviorinfo-table).
